# Capability V2 Single-Database Schema Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在保留 Capability Gateway 治理和十一个领域所有权的前提下，把公司环境落地为一个 `ai00_test` 数据库、十一组 `workmanship_*` 领域表、四个开发账号和一个无 DDL Runtime 账号，并生成可在 DBeaver 审核执行的非破坏性增量 SQL 与逐项验收清单。

**Architecture:** `official_domains.json` 与显式表所有权清单定义领域事实；一个 fail-closed Schema 编译器把所有登记 migration 合并为确定性的期望 Schema；现场 `information_schema` CSV 经过严格表头和数据库名校验后与期望 Schema 比对；SQL 生成器只允许创建缺失表、添加安全字段和添加缺失索引。多数据库配置继续保留为强化模式，新增 `single_database_domain_tables` 部署配置，不把逻辑隔离宣称为物理隔离。

**Tech Stack:** Python 3.12、Pydantic 2、现有 OceanBase/MySQL migration 规范、PyMySQL（仅运行时连接；Schema 工具默认离线读取 CSV）、pytest、JSON/CSV、PowerShell/DBeaver。

## Global Constraints

- 生产与公司测试环境使用 OceanBase 4.3.5+、MySQL 兼容模式和单一业务数据库 `ai00_test`。
- 所有业务表名必须以 `workmanship_` 开头；每张表必须有且只有一个一级领域 owner。
- 十一个一级领域固定为 `base`、`project_management`、`factory`、`craft`、`knowledge`、`ontology`、`agent`、`integration`、`device`、`digital_model`、`simulation`。
- Device 是一级领域；Local Runtime 是 Device 技术组件和消费者类型，不再是一级数据领域。
- Digital Model 与 Simulation 保持独立领域，但可共享同一开发账号。
- 四个人类开发账号分别负责 Craft、Digital Model+Simulation、Device、其余七域；开发账号不持有数据库级 DDL。
- Runtime 账号只有登记表的必要 DML，无 `CREATE`、`ALTER`、`DROP` 或 `GRANT`。
- 禁止自动生成或执行 `DROP DATABASE`、`DROP TABLE`、`TRUNCATE`、`DELETE`、重命名、字段缩窄、删除字段/索引/约束或无回填策略的 `NOT NULL` 新字段。
- 不读取业务行，不读取 DBeaver 密码，不把连接串、密码、`.runtime` CSV/SQL 或执行日志加入 Git。
- 三份用户文件 `CODEX-DESKTOP-HANDOFF.md` 和 `docs/superpowers/reviews/` 下两份审核文件不得修改或暂存。
- 不使用子代理；当前会话按任务顺序内联执行。
