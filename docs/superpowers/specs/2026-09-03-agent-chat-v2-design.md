# Agent Chat Capability V2 Design

## Review correction

`agent.interaction.chat.change.apply@2` governs chat transport only (`chat_stream`, `chat_sync`). The Web confirmation endpoints are not operations of that Capability: after validating an actor/session/tool-bound pending token, they resolve the submitted generated tool name from the pinned Catalog and invoke that target Capability through the Gateway, then continue the conversation through chat @2. Legacy tool names are rejected rather than inferred. Agent Web envelopes use the Base adapter and the fixed consumer id `ai00.web.agent`; legacy error dictionaries become declared business errors instead of successful opaque output.

## Change classification

- Type: breaking contract correction delivered as a new major Capability version.
- Reason: `agent.interaction.chat.change.apply@1` is stable and freezes a strong-transaction, required-evidence, user-confirmation contract whose closed schemas do not match the existing Xiaorou Web consumers. Changing those fields in place would violate Capability V2.5 compatibility rules.

## Capability identity

- Existing version: `agent.interaction.chat.change.apply@1`; remains registered and unchanged.
- New version: `agent.interaction.chat.change.apply@2`.
- Domain and owner: `agent` / Agent Provider.
- Lifecycle target: stable after deterministic checks and trusted business approval.
- `capability_version_gid`: generated by the existing Descriptor adapter from the exact `@2` identity and recorded in the refreshed Catalog.

## Business definition

The Capability accepts one authenticated Agent chat or confirmation interaction and returns its bounded response to the initiating consumer. Chat submission may append Agent-owned session history and invoke an external model, but it does not itself approve any business-domain mutation.

Invariants:

1. Actor identity comes from the trusted invocation envelope; caller-supplied `user_gid` is discarded.
2. A supplied session must belong to the authenticated actor.
3. Chat submission never bypasses confirmation required by an invoked write tool.
4. Stream output is bounded to 500 serialized SSE events; synchronous compatibility output is carried as bounded JSON text inside the closed Capability contract.
5. Context is serialized by the first-party Web adapter and decoded only inside the Agent Provider.

Inputs:

- `operation`: `chat_stream`, `chat_sync`, `confirm`, or `confirm_sync`.
- `body`: closed object containing the applicable message, session, confirmation, tool, authentication, and `context_json` fields.
- `ai00_token`: optional compatibility token.

Outputs:

- `data.events` plus `data.media_type` for streaming interactions; or
- `data.response_json` for synchronous compatibility responses.

Stable errors remain the existing Agent domain error set. Invalid operation, malformed context JSON, unknown fields, and session ownership failures remain caller-visible rejections through existing Gateway mappings.

## Execution and authorization

- Side effect: `write`, because Agent session history may change.
- Consistency: `eventual`; external model calls and session history are not one atomic database transaction.
- Evidence: `optional`; durable Gateway outcomes remain available without inventing domain evidence.
- Chat-level confirmation: `none`; write tools invoked during chat retain their own confirmation tokens and policies.
- Idempotency: required at the Gateway; the Web adapter continues deriving the key from request identity when the caller omits one.
- Permission: `agent.interact`.
- Exposure: existing Web/API/plugin/agent/MCP exposure is retained.
- Data classification: confidential; context and responses must not be logged as Gateway diagnostics.

## Versioning and consumer migration

The Provider registers both majors concurrently. Version 1 keeps its frozen Descriptor, schemas, and handler binding so existing pinned consumers remain resolvable. Version 2 receives the corrected policy and schemas.

The first-party routes `/api/ai/chat`, `/api/ai/chat/stream`, `/api/ai/confirm`, and `/api/ai/confirm/sync` pin major version 2. The shared Web compatibility envelope builder gains an optional `major_version` argument defaulting to 1, preserving every existing caller.

The Agent router:

- removes caller-supplied `user_gid`;
- serializes `context` into `context_json` before Gateway validation;
- restores synchronous JSON responses; and
- rehydrates bounded event arrays into an SSE `StreamingResponse`.

No table or migration change is required. The existing Agent session repository and model runtime remain the execution dependencies.

## Implementation boundary

Owner-domain changes:

- Agent chat Capability registration and Provider descriptors.
- Agent chat Web compatibility router.
- Agent Provider and boundary tests.

Approved shared-platform change:

- Add the backwards-compatible `major_version=1` parameter to the existing Web compatibility envelope builder and its tests.

Generated/governance changes:

- Register `@2` in the acceptance manifest and generated Catalog/docs.
- Update the four Web route inventory bindings to target major 2.
- Refresh Agent Provider artifact hashes only after source is stable.
- Preserve `@1` Catalog content byte-for-byte at the Descriptor level.

## Verification

TDD sequence:

1. Prove `@1` remains identical to the currently published Descriptor.
2. Prove `@2` traverses the real Gateway with a non-transactional Provider and does not return `transaction_participant_required`.
3. Prove super-admin and member identities receive `agent.interact`, while external identities do not.
4. Prove the Web adapter pins major 2, strips `user_gid`, accepts context, restores SSE, and restores synchronous JSON.
5. Run Agent Provider tests, route inventory tests, generated-artifact checks, domain dependency checks, and all seven mandatory acceptance cases for both retained `@1` and new `@2` where applicable.

Runtime verification requires restarting the backend with the refreshed signed Catalog and exercising Xiaorou through the real authenticated Web surface. It must remain independent from unit and acceptance evidence.

## Governance and approval

- `machine_passed`: unverified until the new Catalog, acceptance manifest, and deterministic checks are complete.
- `human_approved`: unverified. A chat assertion of super-admin status is not approval.
- `runtime_verified`: unverified until controlled authenticated runtime evidence is captured.
- `advisory`: true.

After Catalog generation, the exact `@2` `capability_version_gid`, `business_definition_hash`, Snapshot, and reason must be submitted through the trusted server-authenticated super-admin review workflow. This coding task must not manufacture or infer that approval. Release remains blocked if the trusted approval is absent.

## Alternatives rejected

- Mutating `@1` in place: deterministically breaking under V2.5.
- Marking chat as read-only: false because session history changes.
- Faking a transaction participant or evidence: misrepresents runtime guarantees.
- Bypassing the Capability Gateway and calling the legacy route directly: removes the required authorization and audit boundary.

## Unresolved risks

- Existing third-party consumers pinned to `@1` are not runtime-verified; retaining `@1` avoids forced migration.
- Business approval and controlled runtime verification remain external human/server steps.
- Full repository checks may still report unrelated pre-existing failures; Agent-scoped results must be reported separately.
