# 同步更改规格自审记录

2026-09-14；审查对象：主规格 v0.2、大规模专项 v0.1。方式：同一作者按需求追踪、故障注入场景与反例审查；不是独立审查、不是运行测试或治理批准。

## 1. 自审发现并补齐的缺口

| 缺口/反例 | 修订落点 | 处理 |
| --- | --- | --- |
| 每文档串行仍可能同时进入同一 UI 线程 | 专项 §2、§6 | 改为进程级串行，文档级队列 |
| 10ms 片被单个冷调用或巨大子列表绕过 | §4、§6 | 子列表游标、不可抢占边界、watchdog、明确降级 |
| 一万 AH 与十万节点是不同负载 | §1、§10 | 四种规模分别验收，不只测节点总数 |
| 持续输入导致内存队列无限增长 | §5 | 持久化队列、有界预取、高低水位和磁盘失败语义 |
| 合并队列可能吞掉已执行/未知结果 | §3、§5 | 只合并未派发；未知结果先读回，审计保留 |
| 裸 offset 分页会漏节点并误判删除 | §3、§4 | 固定观测/版本游标、manifest 闭合、缺页拒绝 complete |

| 多客户端接管造成两个原生写执行器 | §8 | 租约、fencing、每片派发检查和在途重核验 |
| 程序写期间屏蔽监听吞掉人工修改 | §7 | 精确预期读回确认回声，不按时间窗口忽略 |
| 无通知下“5秒同步”实际无法覆盖万份 AH | §7、§10 | 5秒只启动片，报告轮转延迟；不作虚假时限承诺 |
| 巨量结构前端全量 render 仍阻塞 | §9 | 虚拟化、分页、差量 patch、通知节流 |

| 强杀/磁盘满导致“已保存”误报 | §8 | 未保存窗口、不能丢弃的队列与显式风险退出 |
| 单次热读取成绩被当成生产 SLA | §10、§11 | 冷热分测、指标分层、端到端验收和未验证门槛 |
| 合并完成后、实际写入前又发生手工修改 | §7 | 紧邻调用前置条件核验；消息重入/事务能力单列门槛 |
| 每片网络鉴权反而造成大量请求，服务端 fencing 被误认为原生锁 | §8 | 本地有效期/代次验证、异步续租、原生唯一执行器与撤销传播边界 |

## 3. 反例检查结论

- 一节点从父 A 移到父 B，同时另一侧删除 B：必须冲突，不生成悬空父关系。
- 一次创建 100,000 个兄弟：页内项数与片内调用预算共同限制，不能假称一个父节点就是一个小任务。
- 原生创建已成功但返回超时：进入 outcome_unknown，读回映射后确认或人工处理，不二次创建。
- A 切 B 后 A 回包：归 A 账本，不更新 B 的当前画面/环境。
- 两个同名文档或重复零件：按会话/来源实例身份识别，名称不能替代身份。
- 第 N 页源数据变化、缺页或 E_PENDING：partial/stale，不构造删除差异。
- 无事件通知且有万份 AH：轮转延迟可见，不承诺所有变化立即回收。
- 关闭前手工动作未读取：必须承认无法保证恢复，不将缓存当已持久化。

上述为设计检查，尚未运行对应故障注入或真实环境测试。

## 4. 仍未解决的技术事实

1. 安全异步结构补取入口、单次冷调用最大阻塞尚未验证；可能影响“模型全程可交互”。
2. 原生 AH 事件范围、子节点全部 CRUD 和无激活后台访问尚未验收。
3. 在线配置/实例身份能否跨会话准确重开尚未验证。
4. 已知一个 CPS E_PENDING 节点的服务端/驻留失败根因未确定。
5. 新合同的实际注册、GID、权限、租约、存储迁移和 Provider 绑定需实施时按权威源核实；规格未伪造这些状态。

这些不是用文档可以消除的问题，已写成实施/发布门槛和失败行为。审查结论：对当前用户需求已建立明确覆盖关系，发现的设计遗漏已补充；不能宣称没有任何缺漏，也不能宣称性能或正式同步已通过。

## 5. 文档检查实际结果

对三份规格执行了相对 Markdown 链接存在性检查及 TODO/TBD/待填写标记检查：链接目标存在，未发现未填标记。另核对容量、partial/complete、取消与回滚、冷模式和治理状态的跨文档表述。该检查仅证明文档结构与引用，不证明软件行为或设计绝对正确。
