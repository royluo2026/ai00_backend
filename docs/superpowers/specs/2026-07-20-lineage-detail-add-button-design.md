# 工艺流程图详情关系卡片新增按钮统一设计

## 背景

工艺流程图详情面板中的关系卡片在新版 `_renderRels` 实现中已经切换为基于 ontology schema 的动态分组模型，但新增按钮的可点击判断仍沿用旧版白名单逻辑，导致 `需求工具`、`需求工装` 以及其他同类关系卡片出现 `+` 按钮不可点击或误禁用。

受影响代码位于 `dist/packages/craft-plugin/web/lineage_view/layout_detail_panel.js`，主要问题集中在新版 `_renderRels(gid, mountEl = this._relsBody)` 这条渲染链路。

## 目标

统一详情面板关系卡片的新增规则，使所有在详情面板中展示的有效关系分组都按同一模型控制 `+` 按钮状态和点击行为，修复 `需求工具`、`需求工装` 及其他同类卡片的新增入口不可点击问题，同时不影响只读权限控制和子节点新增逻辑。

## 非目标

- 不调整 `_openAddDetail` 中各类候选数据源的现有分流规则。
- 不改动详情面板之外的其他页面或其他业务流程。
- 不新增新的关系类型配置字段或后端接口。

## 设计

### 1. 统一关系分组模型

新版 `_renderRels` 中展示的关系分组已经全部由 `groups` 数组承载，其中普通关系组统一包含 `linkType` 和 `linkTypes`。这次修复以该模型为准，不再依赖旧的硬编码白名单来判断某类关系是否支持新增。

规则如下：

- `child` 分组继续按现有子节点逻辑处理。
- 其他关系分组只要存在有效 `grp.linkType`，就视为可发起新增。
- `+` 按钮是否禁用仅由以下条件决定：
  - 当前线体是否可编辑；
  - 当前分组是否存在有效新增目标（`child` 或有效 `linkType`）。

这意味着像 `project_tools`、`project_tooling` 这类当前通过 schema 显示到详情面板中的关系，不再需要额外补白名单。

### 2. 统一点击行为

新增按钮点击逻辑统一为：

- `child`：继续通过 `CHILD_TYPE_MAP` 推导子节点类型并调用 `_openAddDetail`。
- 其他关系分组：直接使用 `grp.linkType` 和 `grp.name` 调用 `_openAddDetail(key, gid, grp.linkType, grp.name)`。

这样可以让详情面板中的所有关系卡片使用同一条新增入口链路，不再因为“内置关系 / 动态关系”来源不同而分叉。

### 3. 同步修复同文件中的同类关系面板实现

`layout_detail_panel.js` 内仍保留了多处相似的关系面板渲染实现。为了避免出现一个入口修好、另一个入口仍沿用旧规则的情况，需要把同样的新增判断统一到这些同类实现中。

目标不是大规模重构，而是保证当前文件内所有关系卡片新增入口遵循一致规则：

- 以当前分组对象上的关系类型为准；
- 不再依赖过时白名单；
- 只读权限继续生效。

## 兼容边界

以下行为保持不变：

- 当前线体无编辑权限时，`+` 按钮继续禁用，并保留现有只读提示。
- `child` 分组继续按当前子节点新增逻辑工作。
- `_openAddDetail` 中工具、工装、设备、问题、任务等候选源加载方式保持原样。

## 验证

至少验证以下结果：

1. `需求工具` 卡片的 `+` 可点击。
2. `需求工装` 卡片的 `+` 可点击。
3. 其他通过 schema 显示在详情面板中的同类关系卡片，只要存在有效 `linkType`，`+` 也可点击。
4. 只读线体下，上述按钮仍保持禁用。
5. 子节点 `+` 行为不回归。
6. 文件中其他同类关系面板实现不再保留旧白名单分支。

## 风险与控制

主要风险是把原本确实不应支持新增的关系也放开。此次通过“必须存在有效 `linkType`”这一条件来约束入口范围，并保留 `_openAddDetail` 现有分流逻辑，避免扩大本次变更的业务范围。

另一个风险是同文件内多套相似实现行为不一致，因此本次会同步检查并统一这些入口，避免修复不完整。
