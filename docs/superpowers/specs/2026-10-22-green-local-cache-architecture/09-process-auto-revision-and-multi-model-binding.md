# 09 工艺自动技术修订与同版工艺多数模适配

状态：详细设计草案。允许同一精确工艺快照适配多份产品配置；不依赖用户记得手动升版维持正确关联。

## 1. 四个独立维度

| 维度 | 何时变化 | 固定什么 |
|---|---|---|
| 业务发布版本 | 经明确发布流程命名 A/B/TG0 等 | 指向已发布不可变技术快照 |
| 自动技术修订 | 每次有效工艺内容／结构提交 | 完整工艺状态、父修订和内容摘要 |
| 数模配置快照 | TC 配置／实际解析结果改变 | 实例、工程版本、位置和文件身份 |
| 绑定方案及修订 | 适配不同模型、修改端点／角色或关系 | 精确工艺快照、目标配置和关系集合 |

流程图布局单独修订；卡片移动不强迫工艺内容升修订。仅上传结果也不应改工程结构版本。业务标签不可用于精确关联。

## 2. 自动修订触发

工艺内容／结构包含增删移工位／工序／操作、顺序和业务连线、零件／资源需求、工艺参数及文字等所属业务字段。每次有效保存由服务端事务校验 base revision，保存变更并生成不可变技术修订、父引用、规范化摘要、actor、mutation_id 和变更序号。

这里的“保存”是一次有边界的业务变更集，不是每个键盘输入、鼠标移动或后台轮询；前端可合并未提交输入，但不能合并跨越他人提交的正式历史。

幂等重试返回同一修订；规范化后无业务变化不生成空修订。技术修订身份不靠时间戳唯一性，显示顺序号只是辅助。冲突提交不生成伪成功修订。云端不可变记录／成员清单可复用既有 BOP 修订体系，不要求每次全量复制所有节点。

本地未联网输入是临时草稿身份；不能把本地编号显示为云端确认修订。跨端正式内容提交必须遵守同一服务入口与事务规则，不能只给桌面自动修订而允许网页覆盖。

## 3. 用户忘记业务升版

若 A版已发布并指向 r8，用户继续修改，系统派生工作草稿 r9…r12；A版仍指 r8。UI 显示“基于 A版 · 未发布修订12”，不能显示 A版已经变成 r12。

发布时用户选择新业务名称，发布对象固定技术修订；发布名称变更不改变已有内容身份。若既有发布流程允许特殊重发，必须建立新的发布记录并留历史，不原地重指旧记录。

允许使用未发布修订进行工作仿真或明确的阶段记录，前提是界面／结果／基线带工作状态，不能冒充正式发布版。哪些状态可以成为正式阶段基线由项目策略和治理决定。

## 4. 同版工艺多目标方案

合法例子：

```text
BOP A版的精确快照 r8
 ├─ 方案 S1 / 修订1 → TG0 数模快照 M0
 ├─ 方案 S2 / 修订1 → TG1 数模快照 M1
 └─ 方案 S3 / 修订2 → 同工程版本另一变量配置 M2
```

不需要为了新增 S2 升工艺内容版本或复制整份流程图。S1 和 S2 分别保存，不后来覆盖以前。方案可以引用明确的多个模型／资源集合；唯一性不能设计为一个 BOP 只能有一个 model_version 或一个 active_binding。

方案维度包括：工艺快照、目标配置组合、业务用途／场景、方案身份、关系集合、方案修订、状态和证据。相同端点可以有不同合法用途，重复操作则按幂等和已定义业务约束判定。

工作场景使用明确选择的方案及修订；个人当前选择保存在会话／工作场景上下文，不更新一个全用户共享的“最近绑定”。若要保存团队默认方案，单独版本化且执行开始固定该值。

## 5. 精确执行组合

每次检查、截图、回填和冻结固定：`process_technical_snapshot + model_configuration_snapshot(s) + binding_scheme_revision + workspace/model_set mapping + execution_policy`。

执行前验证方案确实针对该工艺快照和目标配置。即使两个工艺快照显示同一 A版标签也不能仅凭名称兼容。多个适用方案且当前未选定时要求明确选择；不能按最后更新时间、当前原生文档或同名件自动决定。

执行中切换 UI 所看方案不改变已有任务。更换任务输入需停止／派生新任务；结果依然回到原精确版本或产生明确冲突，不自动挂到新方案。

## 6. 工艺变化后的方案派生

从 r8 改为 r12 时，旧方案依然属于 r8。可以派生新的候选方案并生成迁移清单：

- 需求、稳定工序身份、绑定语义和目标依赖均可证明未变的关系，可自动迁移并记录继承证据。
- 文字／布局等不影响绑定的变化不要求重新人工匹配所有零件，但新方案仍明确适用 r12。
- 零件需求、角色、操作归属或目标配置变更的关系进入待复核／失效。
- 节点删除保留旧关系历史；新节点同名不能自动继承删除节点绑定。
- 未确认候选不能计为已验证，更不能为了不中断演示而默默采用。

“可复用绑定”与“同一方案直接改指新工艺”不同；必须保留新旧版本和迁移证据。摘要可分依赖范围，不能把所有文字修改都变成全线重绑，也不能把真正需求变化忽略。

## 7. 冻结、比较与冲突

TG0 manifest 固定 r8/M0/S1，TG1 可以是 r8/M1/S2 或 r12/M1/S4。第一种表达工艺不变而产品升级，第二种表达两者都变化；比较要显示这个区别。

冻结后修改方案产生新修订，不能改旧 manifest。其他人修改同一方案用 expected scheme revision 检查；同时修改工艺草稿用 expected technical head 检查；不要求这两个独立版本同号递增。

## 8. 提醒与状态

推荐摘要：“工艺 A版 · 已发布 r8 | TG1 配置 | 方案 S2 v1”；草稿：“基于 A版 · 未发布 r12 | TG1 配置 | 派生方案待复核”。

工艺没变仅新增模型适配时正常创建方案，不误报用户忘记升版。工艺变了但没发布时提示内容与发布快照不同。需求变化展示受影响绑定数量和处理入口，不强迫一次性补齐所有未确定匹配才能保存草稿。

## 9. 迁移和验收

历史数据仅有 A版名称、无技术快照时标 provenance incomplete，不能反推出可信旧内容。可从当前内容建立迁移起点，但不能伪造过去时间的快照或把所有旧绑定当已验证。

- PR01：A/r8 绑定 M0、M1 两方案共存，分别可执行并从其他端查询。
- PR02：改内容不点击升版，自动产生 r9；旧 r8 与其基线保持不变。
- PR03：同请求重试／无内容变化不产生重复空修订。
- PR04：仅布局或新附件不改变工艺结构修订与模型身份。
- PR05：同名新工序不继承已删除工序绑定；合法不变关系可以有证据迁移。
- PR06：两个用户切换方案互不改变对方任务，旧结果不挂到新方案。
- PR07：离线草稿联网冲突可保留比较，不覆盖云端头。
- PR08：旧数据缺失历史快照明确提示，不能冒充可审计历史。
