# Capability 治理与测试中心设计

## 1. 背景与问题

Capability V2 已具备 Catalog、Provider、Gateway、领域数据库、消费者暴露、审计和严格离线验收，但现有测试层之间存在断层：离线 success 用例主要验证最小输入是否符合 JSON Schema；应用测试普遍使用内存 Fake Repository；路由测试通常替换认证、Gateway 或数据库连接。因此，测试可以全部通过，却仍可能在真实组合路径中出现以下问题：

- 旧 Web 路由未携带确认令牌，真实写入返回 `confirmation_required`。
- Fake Repository 返回 Python 字典，而 OceanBase 驱动返回 JSON 字符串，更新路径发生类型错误。
- 只验证创建，没有验证读取、更新、状态迁移、删除和残留。
- Capability、Provider、API、内部接口、数据库和测试之间的映射缺失或漂移。
- 离线契约报告被误解为真实运行联调报告。

本设计建立仅部署在开发测试环境的“Capability 治理与测试中心”，把能力实现关系、变更审批、自动测试、运行健康和发布证据收口为一套可机器验证的机制。

## 2. 目标

1. 自动建立并持续核对 Capability 与 Provider、消费者入口、内部接口、数据库及测试证据的完整实现关系。
2. Agent 或开发者修改相关代码后，自动在测试环境 UI 的“已发现变更”区显示差异和缺口。
3. 新增或修改稳定 Capability 时实施失败关闭的测试与审批门禁。
4. 日常提交运行快速门禁；仅在正式发布前运行真实 OceanBase 全量读写 E2E。
5. 提供管理员可见的能力治理、实现覆盖、运行健康、变更审批和发布验收 UI。
6. 物理隔离测试治理代码与生产制品，保证治理 UI、扫描器、DDL 清理和测试凭据不进入生产包。
7. 接管当前 264 个稳定能力作为已批准基线，不制造无意义的全量待审记录。

## 3. 非目标

- 不在生产环境部署治理 UI、源码扫描器、主动探针或测试编排器。
- 不承诺消灭所有业务缺陷、浏览器布局缺陷、外部系统故障或性能问题。
- 不把所有关系强制为数量相等的一对一映射。
- 不允许治理工具成为产品运行路径、跨域 SQL 捷径或应用 DDL 依赖。
- 不安排每晚真实 OceanBase 全量 E2E。

## 4. 核心原则

### 4.1 完整关系图，而非伪一对一

Capability 与接口是受控的多对多关系。一个聚合 Capability 可以通过受控 `operation` 承载多个业务动作；一个 Capability 也可以同时暴露给 Web、Plugin、Agent 或 MCP。治理标准是每个节点和每条边都有明确声明、可追溯来源和有效证据，而不是强迫数量一致。

### 4.2 声明、实现、证据三者独立核对

- 声明：Catalog Descriptor、领域清单、暴露策略、权限、确认、幂等和测试画像。
- 实现：Provider 注册、handler、消费者入口、Domain Port、Repository、表和迁移。
- 证据：契约测试、Provider 测试、消费者测试、真实 E2E、被动指标和探针。

三者任一缺失或版本不一致都形成 Finding，不能用另一层的成功替代。

### 4.3 失败关闭发布，运行故障隔离

治理中心不可用时不得影响现有 Gateway 的业务调用，但不得批准新 Catalog Release 或构建生产制品。治理能力是发布控制平面，不是业务数据平面。

## 5. 环境与物理制品隔离

### 5.1 测试制品

测试制品包含：

- 正式业务后端和前端。
- Capability 治理后端包。
- 管理员治理 UI。
- 工作区扫描器和隔离运行时检查器。
- 快速测试编排器。
- 发布前真实 E2E 和精确 DDL 清理工具。

### 5.2 生产制品

生产制品仅包含正式业务运行代码和轻量发布凭证校验器。生产环境不包含：

- 治理 UI 和导航入口。
- 工作区、Git 或源码扫描代码。
- 测试编排器、测试画像夹具和主动探针。
- DDL 清理逻辑、测试数据库驱动配置和测试身份。
- 待审变更、扫描缓存和完整测试报告。

生产启动时只校验：批准的 Catalog Release、Provider artifact hash 和最低数据库迁移版本。校验不通过时新版本拒绝启动，部署系统保留或回滚到旧版本。

### 5.3 构建保证

同一仓库生成两个物理不同的制品。生产制品使用文件白名单构建，不能通过“测试包关闭功能开关”生成。生产构建门禁必须解包验证：

- 禁止目录、模块、静态资源和依赖不存在。
- 生产 OpenAPI 不存在治理接口。
- 前端资源清单和导航不包含治理入口。
- Python import graph 不引用治理包。
- 不包含 `.env`、测试凭据、临时报告、测试数据或 DDL 工具。
- 制品内容清单、hash 和签名与发布记录一致。

生产服务必须从签名后的生产制品启动，不能直接指向 Git 工作区或测试目录。

## 6. CapabilityImplementationGraph

扫描器生成版本化的 `CapabilityImplementationGraph`。每次扫描绑定以下基线：

- Git commit 或工作区内容摘要。
- 上一个已批准 Catalog Release。
- 当前生成 Catalog Release。
- Provider artifact hashes。
- OpenAPI 摘要。
- 数据库迁移清单摘要。
- 测试画像清单摘要。

### 6.1 节点类型

- `capability`：ID、Major、生命周期、领域和 Descriptor hash。
- `provider`：官方 Provider、版本、artifact hash 和注册入口。
- `handler`：Capability 对应的实际处理函数。
- `operation`：聚合 Capability 下受控业务动作。
- `exposure`：REST、legacy Web、Plugin Mount、Agent、MCP 或本地运行时入口。
- `domain_port`：正式跨领域接口。
- `repository`：领域持久化边界。
- `database_account`：领域运行账号和 DDL 账号角色，不保存凭据。
- `table`：领域表和归属。
- `migration`：领域迁移文件和版本。
- `test_profile`：测试画像和夹具版本。
- `test_case`：具体测试定位符。
- `evidence`：测试、探针、被动指标或发布报告。

### 6.2 关系类型

- `implemented_by`
- `registers`
- `dispatches_operation`
- `exposed_through`
- `consumed_by`
- `depends_on_port`
- `persists_through`
- `owns_table`
- `introduced_by_migration`
- `verified_by`
- `supersedes`
- `compatible_with`

每条关系记录来源文件、行号或运行时注册证据、首次发现版本、最近确认版本和状态。

### 6.3 关系状态

- `verified`：声明、实现和证据一致。
- `missing`：声明存在但实现或证据缺失。
- `orphaned`：实现或接口存在但没有正式声明。
- `conflicting`：领域、版本、权限、Schema 或归属冲突。
- `unverified`：存在关系但从未执行相应验证。
- `stale`：证据对应的代码、Catalog、Provider 或迁移摘要已经变化。
- `waived`：存在有效、未过期且范围精确的豁免。

## 7. 扫描与输入机制

### 7.1 自动发现

测试环境工作区扫描器监听白名单目录，并进行去抖动合并。Agent 或开发者修改代码后，扫描结果进入 UI 的“已发现变更”，不会自动进入正式审批。

输入包括：

- Descriptor 和 Catalog 生成源。
- 官方领域和 Provider artifact 清单。
- Provider 注册代码和运行时 Registry 快照。
- FastAPI OpenAPI 与路由注册快照。
- Plugin、Agent、MCP 投影清单。
- Domain Port、领域依赖和边界审计。
- Repository、表归属和迁移清单。
- 测试画像、测试用例和验收清单。
- Git diff 或工作区摘要。

### 7.2 静态与动态双扫描

静态扫描负责可审计的文件、AST、清单和引用关系。动态扫描在受限子进程中加载正式应用构建，读取真实 Registry、OpenAPI 和投影结果。动态扫描不得执行工作区任意脚本，只能调用固定入口，并具备超时、内存限制、网络禁用和只读环境。

### 7.3 正式变更单

开发者或 Agent 显式执行“提交审核”后，系统冻结结构化快照，生成不可变变更单。正式变更单记录：

- 基线和目标 Catalog Release。
- 代码与生成物摘要。
- 节点、关系及契约差异。
- 影响的领域、消费者、表、迁移和测试。
- 变更分类和所需批准者。
- 自动检查结果和阻断项。

提交后代码再次变化会使变更单标记为 `stale`，必须重新扫描并生成新修订，原批准不得沿用。

## 8. 变更生命周期与审批

### 8.1 状态机

`detected → draft → submitted → checking → pending_approval → approved → released`

附加终态和分支状态：`checks_failed`、`rejected`、`withdrawn`、`superseded`、`expired`。

### 8.2 变更分类

- 兼容变更：增加可选字段、补充不改变语义的文档或证据。
- 行为变更：Schema 未破坏，但语义、权限、确认、幂等、副作用、数据库或一致性发生变化。
- 破坏性变更：删除或改型字段、增加必填、收紧枚举、删除暴露、改变稳定语义或资源标识。

稳定 Major 禁止原地发生破坏性变更。破坏性变更必须创建新 Major，声明迁移窗口，与旧 Major 并存，并根据实际调用者和安装插件确认可退役时间。

### 8.3 批准矩阵

- 单领域内部变更：领域负责人批准。
- 跨领域共享能力：Provider 领域与受影响消费者领域负责人共同批准。
- 权限、确认、数据库归属、生产暴露或破坏性变更：额外需要平台管理员批准。
- 同一人不能同时作为破坏性变更的提交者和最终平台批准者。

### 8.4 豁免

豁免必须绑定 Finding、Catalog Major、代码摘要、理由、负责人、批准人和到期时间。禁止全局或无限期豁免。代码或契约变化后豁免自动失效；到期后恢复发布阻断。

## 9. 测试画像与门禁

每个稳定 Capability 必须声明且只能选择一个主测试画像，并可附加消费者画像：

- `read`：最小成功读取、空结果、未授权、资源范围拒绝和输出类型。
- `crud`：创建、读取、更新、幂等重放、删除或归档、不可见及精确残留检查。
- `state_transition`：合法状态迁移、非法迁移、乐观锁冲突和重复请求。
- `async_job`：创建、状态轮询、成功或可解释终态、取消、重复提交和超时。
- `external_connector`：配置验证、网络隔离下的可解释失败、测试替身契约及发布前可用性检查。

附加消费者画像包括 `rest`、`legacy_web`、`plugin_mount`、`agent`、`mcp` 和 `local_runtime`。

### 9.1 日常快速门禁

在 Capability、Provider、Repository、迁移、消费者入口或治理声明变化时自动运行：

- Catalog 与 Schema 兼容性。
- 实现关系图完整性和漂移检查。
- Provider handler 真实调用，但使用隔离测试 Repository。
- Repository 边界编解码测试，覆盖 OceanBase 可能返回的 JSON 字符串、`Decimal`、日期时间、布尔、字节和空值。
- 受影响消费者入口测试。
- 权限、确认、幂等和错误映射。
- 测试画像与测试定位符完整性。
- 生产制品排除规则的静态检查。

Fake Repository 不得自行美化数据库类型；驱动形态夹具由公共测试库提供并版本化。

### 9.2 发布前真实 OceanBase E2E

正式发布前，在测试服务器、真实 OceanBase、计划内领域账号和实际 HTTP 服务上运行。数据库支持的 Capability 必须按照画像完成真实往返，消费者入口必须使用实际协议和身份。旧 Web 路由测试不得额外注入产品前端不会发送的确认令牌。

测试数据使用唯一 `E2E-<release>-<run-id>` 标识，所有对象和外部副作用记录精确 ID。先验证产品删除或归档语义，再由验收工具使用 DDL 账号按精确 ID 反向物理清理，最后查询确认残留为 0。DDL 密码只存在于本机进程内存，禁止输出、日志和报告。

发布前报告的 `validation_scope` 必须是 `runtime_e2e`。`contract`、`provider` 或 `consumer` 范围的报告不能批准生产发布。

### 9.3 外部系统和不可执行能力

外部系统暂不可用不能用“跳过”伪装通过。结果必须为：

- `passed`：真实目标或批准的沙箱验证成功。
- `expected_unavailable`：符合明确、已批准的发布条件，且错误分类和降级行为通过。
- `blocked`：发布所需外部依赖不可用。

稳定 Capability 不允许没有测试画像或以永久 `contract_only` 代替运行证据。

## 10. 健康模型

### 10.1 数据来源

- 实时被动指标：复用 Capability audit ledger，聚合调用次数、成功率、错误类型和延迟，不保存业务 Payload。
- 每 5 分钟只读探针：验证 Catalog、Registry、Provider、领域连接和安全的只读能力。
- 管理员按需检测：指定领域、Capability 或消费者入口。
- 发布前全量 E2E：唯一允许主动执行完整写入画像的自动流程。

### 10.2 状态

- `healthy`：实现图完整且有近期有效成功证据。
- `degraded`：错误率、延迟、依赖或证据接近阈值。
- `broken`：实现缺失、映射冲突、探针失败或发布门禁失败。
- `unverified`：从未获得相应层级证据。
- `stale`：最近证据已被代码、Catalog、Provider 或迁移变化失效。

健康状态必须同时显示证据层级和时间，禁止用近期契约测试覆盖过期的真实 E2E 状态。

### 10.3 指标保护与性能

指标按 Capability、Major、消费者类型和错误代码聚合，禁止使用用户 ID、资源 ID或 Payload 作为高基数标签。查询使用预聚合窗口；治理 UI 不直接扫描审计明细。治理采集失败只写有界告警，不阻塞业务请求。

## 11. 管理员 UI

UI 仅在测试制品中注册，权限为独立的 `system.capability.govern`，不复用普通插件管理权限。

### 11.1 总览

- Catalog Release、代码摘要和最后扫描时间。
- 稳定能力、完整实现、缺失、冲突、未验证、过期证据数量。
- 11 个领域健康状态。
- REST、legacy Web、Plugin、Agent、MCP 和内部 Port 覆盖。
- 最近发布门禁和阻断原因。

### 11.2 实现关系

按领域、Capability、消费者和状态筛选。详情展示 Descriptor、Provider、handler、operation、入口、Domain Port、Repository、表、迁移、测试和证据的完整链路，并链接到来源文件和行号。

### 11.3 已发现变更与待审

- 未提交工作区变化显示在“已发现变更”。
- 显式提交后进入“待审核”。
- 显示新旧契约差异、影响范围、测试选择、缺失项和批准矩阵。
- 支持提交、撤回、批准、拒绝和重新检查。
- 重复点击由幂等键抑制；过期页面不能覆盖新扫描结果。

### 11.4 健康与验收

- 被动成功率、延迟、最近错误和证据年龄。
- 立即执行只读检测。
- 按领域执行受控测试。
- 平台管理员触发发布前全量 E2E。
- 实时查看阶段进度、清理状态和阻断项。
- 下载去敏后的签名报告。

## 12. 数据持久化与审计

治理数据归 Base Platform 所有，建议使用独立测试环境表：

- `workmanship_base_capability_scan_runs`
- `workmanship_base_capability_findings`
- `workmanship_base_capability_change_proposals`
- `workmanship_base_capability_change_reviews`
- `workmanship_base_capability_test_runs`
- `workmanship_base_capability_test_results`
- `workmanship_base_capability_waivers`

大型关系图和报告正文存入受控对象存储，数据库只保存摘要、hash、状态和对象引用。批准、拒绝、豁免、发布和清理均写不可变审计记录。测试环境保留最近 90 天明细和长期发布摘要；删除过期明细不得删除已发布版本的签名摘要。

## 13. 安全边界

- 治理接口只允许测试环境管理员访问。
- 扫描路径使用仓库根下的固定白名单，拒绝符号链接逃逸和任意路径参数。
- 动态检查在无网络、只读文件系统、无生产凭据的受限子进程执行。
- 主动只读探针使用专用最小权限身份。
- 发布前写入 E2E 使用短期测试身份和领域账号；DDL 只用于精确清理。
- 所有报告对 URL、用户名、密码、令牌、Payload 和个人数据进行结构化脱敏。
- UI 不允许提交任意命令、Python 表达式、SQL 或探针 URL。
- 扫描和测试任务有并发上限、超时、取消、心跳和孤儿任务回收。

## 14. 风险与优化

### 14.1 动态注册漏扫

仅做静态搜索会遗漏条件注册和组合路由。通过静态 AST 与受限运行时 Registry/OpenAPI 快照交叉核对；不一致本身形成阻断 Finding。

### 14.2 测试假阳性

测试替身可能与真实驱动不同。公共驱动形态夹具、Repository 编解码契约和发布前真实 OceanBase 往返共同约束。测试证据绑定代码、Catalog、Provider、迁移和夹具 hash，任一变化即过期。

### 14.3 测试数据污染

软删除不等于清理。每次运行维护资源账本，采用唯一 ID、反向清理、失败重试和最终 DDL 精确清理；残留非零直接阻断发布并产生告警。

### 14.4 并发和重复执行

发布前全量 E2E 使用环境级租约，同一测试数据库只允许一个写入验收运行。扫描和只读测试可并行但必须绑定工作区摘要；摘要变化后结果作废。

### 14.5 健康检查制造负载

实时健康只使用被动指标，每 5 分钟探针仅执行有界只读操作。写入测试只由管理员或发布流程触发。探针使用抖动和退避，避免故障期间放大流量。

### 14.6 豁免失控

禁止永久、全局和无责任人的豁免。豁免有最长期限、精确范围和自动失效规则，并在总览持续显示。

### 14.7 治理 UI 给出错误安全感

UI 必须显示验证层级和证据年龄，不能只显示单一绿色。未运行真实 E2E 的能力显示 `unverified`，契约通过不提升为运行健康。

### 14.8 生产夹带测试代码

使用生产白名单制品、解包审计、OpenAPI/资源/import graph 检查和签名内容清单四重防护。部署系统只接受生产制品签名。

### 14.9 回滚不一致

发布记录同时绑定代码、Catalog、Provider 和迁移最低版本。回滚前验证旧 Provider 与向后兼容迁移仍可运行；数据库迁移不可逆时必须提供向后兼容窗口，禁止假定能够回滚数据库。

### 14.10 现有基线噪声

首次启用时以当前已通过严格验收的 264 个稳定能力建立一次性签名基线。基线导入不自动宣称真实 E2E 通过；其运行证据初始为 `unverified`，在首次发布前验收后逐步转为已验证。

## 15. 发布流程

1. Agent 或开发者修改源码和声明。
2. 扫描器生成“已发现变更”和 Findings。
3. 提交者生成正式变更单。
4. 自动执行完整性、兼容性、影响分析和日常快速门禁。
5. 领域负责人及必要的平台管理员审批。
6. 冻结候选 Catalog Release 和 Provider artifacts。
7. 在测试环境执行发布前真实 OceanBase 全量 E2E。
8. 精确清理并确认残留为 0。
9. 生成签名发布凭证和生产文件白名单。
10. 构建、解包验证并签名生产制品。
11. 生产启动校验 Catalog、Provider 和迁移版本后接管流量。

任何步骤失败均不得生成可部署生产制品。

## 16. 验收标准

- 当前 264 个稳定能力全部进入实现关系图，且没有未解释的悬空实现或重复归属。
- 任意新增 Capability 缺少 Provider、测试画像、成功用例或消费者入口测试时构建失败。
- 任意新增 API、旧 Web 路由、Plugin、Agent、MCP 或内部 Port 缺少声明映射时显示阻断 Finding。
- 修改稳定 Schema、语义、权限、确认、幂等或数据库边界时能够正确分类并选择批准矩阵。
- JSON 字符串、`Decimal`、日期时间、布尔、字节和空值边界均有驱动形态测试。
- 发布前报告只能在 `runtime_e2e`、零失败、零跳过、清理残留为 0 时通过。
- 管理员 UI 能显示实现链、来源、测试层级、证据年龄、变更差异和阻断原因。
- 治理中心不可用不影响现有 Gateway 调用，但无法批准或构建新生产制品。
- 生产制品中不存在治理模块、UI、DDL 工具、测试凭据、测试入口或相关依赖。
- 生产启动能够拒绝 Catalog、Provider hash 或迁移版本不匹配的制品。

## 17. 分阶段落地

1. 建立实现关系图、静态/动态扫描和当前能力基线。
2. 建立测试画像、日常快速门禁和证据过期规则。
3. 建立变更状态机、审批、豁免和审计。
4. 建立管理员治理 UI、被动指标和只读探针。
5. 建立发布前真实 OceanBase 全量 E2E、资源账本和精确清理。
6. 建立测试/生产双制品、生产白名单审计和发布凭证校验。

各阶段必须独立可验证；在第五和第六阶段完成前，治理中心只能提供可见性，不能宣称具备完整发布保证。
