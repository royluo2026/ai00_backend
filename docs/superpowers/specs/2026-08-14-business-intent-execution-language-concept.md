# 业务意图与判断型执行语言：概念讨论稿

> 状态：讨论中  
> 日期：2026-08-14  
> 目的：记录 Capability 治理讨论中形成的业务建模与“宽松编程”思想，作为继续讨论和后续正式设计的输入。  
> 本文不是低代码方案、产品实施计划或已批准的最终 Spec。

## 1. 背景

Capability V2 已经把业务操作逐步收敛为可发现、可授权、可审计的正式能力。继续讨论治理机制时，问题从“Capability 是否存在、是否正确实现、被谁消费”扩展到了更上层：

1. 现实业务由哪些目标、流程、活动、参与者和业务对象构成？
2. 一个业务活动是由人工、UI、插件、Agent、自动任务或这些手段的组合完成？
3. 非人工手段具体落到哪个页面、按钮、插件动作或 Agent 工作流步骤？
4. 这些具体手段由哪些 Capability 支撑？
5. Capability 操作的业务“原材料”和产出是什么？
6. 执行过程中使用了哪些知识、参考数据和业务规则？
7. 对于无法提前规则化的工作，如何让 AI 和专家成为受治理的一等执行参与者？

由此形成了一个比 Capability 实现关系图更大的概念：系统不仅描述软件，还要描述现实业务如何被人、AI 和软件共同完成。

## 2. 核心判断

这里所说的“宽松编程”不是低代码，也不是减少正式代码或放松执行约束。

它指的是：

> 程序允许存在无法提前规则化的判断点。这些判断点在运行时由 AI、专家或人机协作完成；程序负责约束目标、上下文、权限、证据、升级条件和后续执行。

传统程序通常假设输入、规则、分支和执行结果可以被提前完整规定。现实业务则经常处于开放世界：

- 目标可以明确，但实现路径不能预先唯一确定。
- 部分步骤可以自动执行，部分步骤依赖专业判断。
- 新材料和新事实会在执行过程中陆续出现。
- 相同业务目标在不同项目、风险和权限条件下可能采用不同计划。
- 专家和 AI 的结论具有来源、置信度和责任边界，不能直接当作客观事实。

因此，合适的编程模型应当是“部分规定、受约束、可持续补全和重新规划”的混合执行模型。

## 3. 业务是拼图，业务流是拼图的组织方式

业务不应被简化为单一固定流程。建议按以下层次表达。

### 3.1 业务目标

描述要实现的结果，例如完成项目投标、形成可发布的工艺基线、完成数模变更后的重新验证、形成可审计的仿真结论。

### 3.2 业务价值流与业务场景

业务价值流描述端到端价值，例如“投标到交付”。业务场景描述其中一种具体情境，例如“设计变更后重新执行工艺和仿真验证”。

### 3.3 业务活动

业务活动描述“要完成什么”，不预先绑定具体实现方式，例如确认项目基线、编制 BOP、发布数模快照、判断当前方案是否具备仿真条件、形成设备准备结论。

业务活动可以被多个业务流复用。多条业务流通过共享活动和业务对象拼成完整业务版图，而不是复制出多套互不相干的流程。

### 3.4 业务对象与交付物

业务对象是活动操作的业务“原材料”和产出，例如：

- 项目与项目基线。
- BOP、受控工艺版本和 craft_commit_ref。
- 数模、模型版本和 model_snapshot_hash。
- 仿真输入、运行记录和仿真报告。
- 设备方案、投标文件和交付包。

治理模型保存业务对象定义、受控引用、关系和摘要，不复制领域数据库中的完整业务数据。

## 4. “业务活动”与“执行手段”必须分离

业务活动描述意图，执行手段描述当前如何完成该意图。一种业务活动可能由人工操作、UI 动作、插件动作、Agent 工作流步骤、定时任务、外部系统、设备程序或这些手段的组合完成。

执行组合需要支持：

- **all_of**：全部执行手段都必须完成。
- **any_of**：选择任意一种合法手段。
- **sequence**：按规定顺序完成。
- **conditional**：根据条件选择手段。
- **manual_gate**：必须经过人工判断、确认或审批。
- **fallback**：首选手段不可用时采用受控替代方案。

人工步骤不能被默认视为自动化缺口。有些人工步骤承担责任确认、专业判断、安全控制或法律授权，必须明确标记为保留人工。

## 5. 非人工执行必须定位到具体动作

“由 Web 完成”“由插件完成”或“由 Agent 完成”粒度不足。正式关系必须具体到：

- UI 应用、页面、组件和按钮或菜单动作。
- 插件 ID、插件版本、插件页面和插件动作。
- Agent 工作流、工作流版本和具体步骤。
- 自动化策略、触发事件和执行动作。
- 外部系统、接口和集成动作。
- 设备、设备程序和受控命令。

每个正式动作应拥有稳定的 Entry GID 和动作标识，不能只依赖容易变化的 DOM Selector、URL 文本或函数名。

~~~text
业务活动：发起仿真验证
执行手段：UI Action
页面：simulation/run
动作：submit_run
动作 Entry GID：840...
消费能力：simulation.run.create@1
~~~

声明关系、静态扫描证据和 Gateway 真实调用证据应分别保存，不能把“声明消费”和“实际消费”混成一个状态。

## 6. Capability 是确定性业务动作

Capability 不是业务目标本身，而是实现业务目标的稳定动作原语。

~~~text
业务目标
  → 业务流
  → 业务活动
  → 执行方案
  → 人工/UI/插件/Agent/自动化的具体动作
  → Capability
  → Gateway / Provider / Repository / 数据库或设备
~~~

Capability 需要声明自己对业务对象的作用：reads、creates、updates、archives、transforms、validates、produces 或 references。

输入输出 JSON Schema 只描述技术数据形态，不能替代业务对象语义。治理关系必须同时知道字段属于什么业务对象、引用的是哪个受控版本、产生了什么业务效果。

## 7. 知识、参考数据与业务规则

知识和业务规则必须分开建模。

### 7.1 知识

知识提供解释、经验或判断材料，例如工艺规范、操作指导书、求解器选型经验、历史案例、专家经验、本体、算法说明，以及低频维护、供其他领域计算或算法引用的参考表。

知识可以被人员或 Agent 检索、引用和解释，但知识本身不必具有强制执行语义。

### 7.2 参考数据集

低频维护的表格应成为正式的 **reference_dataset**，包含唯一 Entry GID、数据集版本、内容 Hash、生效区间、维护领域、责任人、数据来源、质量状态及使用者。

运行证据应记录实际使用的参考数据集版本，避免数据更新后无法复现历史计算。

### 7.3 业务规则

业务规则表达必须遵守或能够确定计算的要求，例如：

- 仿真必须同时绑定受控 BOP Commit 和数模 Snapshot。
- 特定类型的设计变更必须重新验证。
- 高风险结果必须由指定角色审批。
- 写入必须执行权限、确认和幂等检查。

可以规则化的要求应由确定性规则引擎或正式代码执行。AI 不能覆盖硬规则。

## 8. 三类不同性质的执行单元

### 8.1 Capability

执行确定性业务动作。输入、权限、副作用、资源范围和输出受正式契约约束。

### 8.2 Rule / Decision

使用明确规则计算确定性结论。适合决策表、阈值、约束和政策判断。

### 8.3 Judgment

处理无法充分规则化、需要结合情境、知识和专业经验的判断。Judgment 可以由 AI 独立提出、专家独立判断、AI 先分析专家复核、多专家会签或 AI 与专家迭代协作。

Judgment 不是普通函数，也不能伪装为确定性规则。

## 9. Judgment 是语言的一等结构

Judgment 至少需要声明：

- 输入材料和当前事实。
- 允许使用的知识、参考数据和工具。
- 不得违反的硬规则和安全约束。
- 可接受的执行者类型和资格。
- 结构化输出 Schema。
- 置信度和证据要求。
- 必须升级给专家的条件。
- 多方意见冲突时的处理方式。
- 判断结果的有效期。
- 判断结果允许触发的后续动作。

~~~text
judgment evaluate_process_feasibility {
    input:
        project_baseline
        bop_commit
        model_snapshot
        equipment_constraints

    knowledge:
        process_standard@3
        material_reference_table@2026.08
        similar_historical_cases

    constraints:
        controlled_versions_must_match
        safety_rules_must_pass

    executor:
        agent first
        expert required when confidence < 0.85
        expert required when safety_impact = high

    output:
        decision: feasible | conditional | infeasible
        confidence
        reasons
        evidence_refs
        required_actions
}
~~~

## 10. 认识论类型系统

为了避免 AI 输出、专家意见和客观事实混淆，语言除了业务数据类型，还需要表达信息的可信性质：

- **fact**：由正式来源和证据确认的事实。
- **observation**：系统或人员观察到的现象。
- **claim**：尚未确认的主张。
- **agent_judgment**：AI 形成的结构化判断。
- **expert_opinion**：由具备资格的专家签署的意见。
- **decision**：有权限的责任主体作出的正式决定。
- **rule_result**：确定性规则的计算结果。

每项信息应携带来源、形成时间、适用范围、有效期、置信度、证据和责任主体。AI 输出不能直接提升为 fact，专家意见也必须与其责任范围和依据绑定。

## 11. 与现有语言思想的关系

没有一种现成语言完整覆盖本需求，但可以吸收以下思想：

- [BPMN](https://www.omg.org/bpmn/)：表达可以预先规定的流程和协作顺序。
- [CMMN](https://www.omg.org/cmmn/index.htm)：表达顺序不可完全预测、依赖知识工作者和持续变化信息的 Case。
- [DMN](https://www.omg.org/dmn/)：表达可精确规定的业务决策和规则。
- [PDDL](https://planning.wiki/_citedpapers/pddl1998.pdf)：使用目标、动作前置条件和效果支持规划。

建议不直接把其中任何一个标准作为完整解决方案，而是定义一个小型、语义严格的核心语言：

> 面向业务目标、约束、判断和混合执行的语言。

该语言吸收 BPMN 的确定性顺序、CMMN 的开放 Case、DMN 的确定性决策、PDDL 的目标和动作语义，以及 AI00 自身的 Capability、业务对象、权限、证据、AI Judgment 和专家责任语义。

## 12. 初步语言概念

~~~text

artifact

reference_dataset

capability

~~~

语言不一定要求业务人员直接手写。文本 DSL、治理 UI、文档解析和 Agent 对话都可以成为编辑方式，但最终必须编译为同一个版本化、可验证的规范表示。

## 13. 两张相连的图

建议把业务语义和技术实现分成两张相连的图，避免形成一个无法理解的超级关系图。

### 13.1 Business Execution Graph

表达目标、Case、业务流、业务活动、执行方案、业务对象、知识、参考数据、规则、Judgment，以及人工、AI 与系统的责任关系。

### 13.2 Capability Implementation Graph

表达 Capability、Provider、Handler、REST、Legacy Web、Plugin、Agent、MCP、Domain Port、Repository、表、迁移、测试和运行证据。

两张图通过“具体执行动作消费 Capability”以及“Capability 读写业务对象”连接。

## 14. 统一 Entry 与关系模型

治理数据仍使用统一 Entry 主表，而不是按每种资产创建独立业务表。Entry 类型可以逐步扩展为：

- business_outcome
- business_flow
- business_activity
- execution_option
- human_action
- ui_page
- ui_action
- plugin_action
- agent_workflow
- workflow_step
- automation_policy
- capability
- business_object
- business_artifact
- knowledge_asset
- reference_dataset
- business_rule
- judgment_definition

Entry、Entry Version、Relation、Relation Version、Finding、Evidence、Judgment Run、Case Run 和 Lifecycle Event 均使用雪花 GID。

实际项目、BOP、数模、仿真和设备业务数据继续保存在领域数据库。治理台账只保存定义、关系、受控引用、摘要和证据定位。

## 15. 语言运行时与基础设施

若把该思想发展成正式语言，需要相应的语言工具链和业务运行基础设施：

1. 解析器、版本化 AST 和规范化 IR。
2. 业务类型、本体和业务对象注册表。
3. Capability Registry、Gateway 和 Provider Runtime。
4. 规则与约束执行器。
5. 持久化 Case Runtime，支持长时间暂停、恢复和等待新材料。
6. AI Judgment Runtime。
7. 专家任务、认领、会签、授权和升级机制。
8. 版本化知识检索与引用服务。
9. 目标规划、安全模拟和重新规划器。
10. 证据、来源、模型版本和责任审计账本。
11. 异常、补偿、撤回、超时和人工接管机制。
12. 编译检查、测试、调试和治理 UI。

## 16. 编译期与运行期责任

### 16.1 编译期检查

系统应发现：

- 引用了不存在或不兼容的 Capability。
- 输入输出业务类型不兼容。
- 缺少必要业务材料、知识或规则。
- 高风险 Judgment 没有专家升级条件。
- 高风险写操作缺少授权、确认或补偿方案。
- 目标在当前能力集合下不可达。
- 多条硬规则互相冲突。
- Judgment 没有结构化输出或证据要求。

### 16.2 运行期责任

运行时负责：

- 维护 Case 当前状态和目标。
- 调用 Capability。
- 执行规则和硬约束。
- 向 AI 发起结构化 Judgment。
- 向专家派发、升级和会签任务。
- 等待新事实和业务材料。
- 在约束内重新规划。
- 保存每一步使用的业务对象、知识、规则、模型、人员和证据版本。

## 17. Agent 的角色

Agent 可以理解 Case 上下文、检索知识和历史案例、执行 Judgment、在 Capability 图中寻找候选动作组合、识别缺失材料或能力，并提出计划修改和自动化候选。

Agent 不可以：

- 把自己的输出标记为客观事实。
- 绕过硬规则、权限、确认或数据范围。
- 私自扩大知识和工具访问范围。
- 自行批准高风险计划。
- 在未授权的情况下发布或启用新自动化。

## 18. 关键风险

### 18.1 过度建模

不试图一次性描述全部现实，只建模与业务决策、执行、责任和证据有关的部分。

### 18.2 万能配置

复杂算法、关键规则和安全控制继续使用正式代码或规则实现，不能塞入无边界 JSON。

### 18.3 模型脱离现实

声明的 As-Is 流程必须与 Gateway、审计、人工任务和业务数据中的真实执行证据比较，持续发现漂移。

### 18.4 AI 权力扩大

AI Judgment、计划建议、正式决定和 Capability 执行必须是不同状态，不能在一次模型调用中隐式合并。

### 18.5 规则与知识混淆

知识提供判断依据，规则提供必须遵守的约束。两者需要不同的版本、验证和运行语义。

### 18.6 责任主体模糊

每个 Judgment、Decision、Approval 和 Waiver 都必须绑定责任主体、授权范围、有效期和证据。

## 19. 当前建议

1. 将这一方向定位为“业务运行语言”或“业务意图与判断型执行语言”，而不是低代码平台。
2. 先定义小型核心语义和规范化 IR，再讨论文本语法和 UI。
3. 将确定性流程、规则化决策和非规则化 Judgment 明确分层。
4. 将 AI 和专家作为 Judgment 执行者，而不是把二者抽象成普通 Capability。
5. 保留严格的 Capability、安全、数据和审计基础设施。
6. 使用 Business Execution Graph 表达业务，使用 Capability Implementation Graph 表达技术实现。
7. 允许 Agent 提出计划和自动化候选，但正式执行受硬约束和责任审批控制。

## 20. 后续需要继续讨论的决策

1. Judgment 第一版只返回规定类型的结果，还是允许直接修改当前计划？
2. AI 提出的新步骤是“计划建议”，还是可以在低风险范围内自动加入并执行？
3. 专家意见与 AI 判断冲突时采用单一责任人、会签、仲裁还是风险分级策略？
4. As-Is、To-Be 和运行时实际路径如何同时版本化并比较？
5. 文本 DSL 是正式源代码，还是规范化 IR 才是唯一事实来源？
6. 哪些业务对象只登记类型，哪些运行实例需要进入 Case 状态？
7. Judgment 的置信度、证据充分性和失效条件如何定义？
8. 业务流、Case 和 Agent Workflow 的边界如何划分？
9. 第一批真实业务场景选择哪一条，用于验证语言是否足够而不过度设计？

## 21. 与 Capability 治理设计的关系

现有 Capability 治理与测试中心仍然必要，它负责验证确定性执行基础是否完整、可靠和可追踪。

本文提出的业务运行语言位于其上层：

- 下层 Capability 治理回答“动作是否真实存在、能否安全可靠执行、由谁消费”。
- 上层业务运行语言回答“为什么执行、要达到什么目标、在何种情境下由谁判断和选择动作”。

两者应共享统一 Entry、版本、关系、证据和生命周期基础设施，但采用不同的视图、状态机和验证规则。
