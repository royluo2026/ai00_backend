# First cache open: repeated journal replay

The user's rear-suspension checkbox exposed a path missed by the prior warm-document visibility check. The scope required 55 JT files and initially reused one. The first eight-file plan was `vismockup-command-2257d8594b290d4e7c21cf9e7c13d0907cc030c53ef3c890189caf0bcc1d213a`. Native FMS timings for several small files were roughly 0.1–0.3 seconds, while execution events showed about 4.8 seconds between each completed step and the next start. The persisted event archive was 794 MB, in addition to an 85 MB legacy snapshot.

`AppPlanJournal.Append` reread and deserialized the entire event archive before every append. A file step appends both invocation and completion events. This cost accumulated across all files and was independent of the native visibility batching fix.

The journal now remembers the byte offset of its validated tail and reads only appended events. Startup still validates the full persisted history, including the legacy snapshot overlap. A single writer handle spans tail refresh, sequence allocation and durable flush. Sequence, stale-instance and truncation checks remain; no logs are deleted or rewritten.

The new Windows byte-range-lock regression proved the old implementation reread a validated prefix. A truncation regression also failed before the fix. Afterward, 76 targeted journal, crash recovery, batch-plan execution, capture and lifecycle tests passed. The self-contained publish succeeded. Installed ConnectorHost DLL SHA256: `55FDFEB9933224949F9199029318DEF9240705C8156344F84D914BF443431ACD`.

An isolated copy of the real journal measured old append times of 6549, 5122, 4665 and 4982 ms. The fixed version measured 1050 ms on its first append, then 40, 29 and 34 ms. Full startup replay still took 6.4 seconds. Evidence is in workspace `.runtime/journal-tail-benchmark-before.log` and `.runtime/journal-tail-benchmark-after.log`; the benchmark did not append to the live journal.
