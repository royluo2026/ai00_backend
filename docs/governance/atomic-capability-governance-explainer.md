# 看懂 AI00 原子业务能力治理

> 一篇写给业务负责人、产品经理和新加入开发者的科普文。阅读它不需要先懂代码。
>
> 更新时间：2026-09-01；依据《原子业务能力开发治理规范 V2.3》和当前 `test` 分支实现。

## 一、先说人话：Capability 到底是什么

在 AI00 里，Capability（原子业务能力）可以理解为一个**有正式执照的业务服务窗口**。

例如，“查询某个 BOP 版本”“发布一个模型快照”“批准一条权限申请”，都是一个明确的业务结果。窗口必须写清楚：谁负责、谁能来办、要交什么材料、会得到什么结果、可能因为什么失败、是否会改数据、重复提交怎么办，以及出了问题去哪里查记录。

Capability 不是数据库表，不是一个 Python 函数，也不是网页上的某个按钮。一个按钮可能先后调用多个 Capability；同一个 Capability 也可以被网页、插件、Agent、API 和自动任务共同使用。

判断它是否“原子”，最简单的办法是问：它是否只有一个主要业务效果？如果两个动作可以分别授权、分别失败、分别重试、分别审计，通常就应该拆开。

## 二、为什么要治理：不是给代码多套一层壳

没有治理时，系统很容易变成一座没有路牌和交通规则的城市：页面直接找数据库，插件记住某个临时接口，Agent 绕过权限调用内部函数；同一件事有三种入口、四套返回格式。短期看很快，长期则没人敢改。

治理要解决的不是“接口够不够多”，而是五个问题：

1. **边界清楚：** 每个业务结果归哪个领域负责，不能多人共同拥有、无人最终负责。
2. **契约稳定：** 输入、输出、错误、权限、副作用和版本都可预测。
3. **入口统一：** 所有正式消费者都经 Gateway 调用，不能偷偷绕道。
4. **证据可信：** 不是自己声明“测过了”，而是证据绑定当前代码、能力版本和治理快照。
5. **发布可阻断：** 发现越权、漏登记、跨域直连或证据不完整时，系统真的不让发布。

## 三、整套机制由哪些模块组成

![图 2｜AI00 原子业务能力治理全景](atomic-capability-explainer-assets/02-system-map.png)

可以把系统分成八个角色：

| 模块 | 通俗比喻 | 主要作用 |
|---|---|---|
| Descriptor / Contract | 办事指南 | 定义唯一业务效果、输入输出、错误、权限、事务、幂等、副作用、消费者和负责人 |
| Registry | 户籍系统 | 保存能力与具体版本的正式身份，分配不可复用的 `capability_version_gid` |
| Catalog Release | 某一时刻出版的服务目录 | 冻结一组可用能力及其契约、Provider 和哈希，让调用方引用确定版本 |
| Capability Gateway | 统一检查站 | 解析版本，校验输入、权限、资源范围、确认令牌、幂等键和超时，再调 Provider |
| Provider | 真正办事的窗口 | 在所属领域内执行真实业务逻辑，只访问本领域的数据或调用其他领域公开能力 |
| Reliability / Audit | 保险箱和黑匣子 | 管理事务、补偿、结果确认、审计记录和不可伪造的执行证据 |
| Governance Center | 城市治理中心 | 生成快照、Finding、关系图和分析，回答哪里未绑定、哪里冲突、哪里缺证据 |
| Release Gate | 出厂总闸门 | 汇总静态门禁、运行测试、审批和签名证据，决定当前版本能否发布 |

它们不是八套互不相干的工具。Descriptor 告诉 Gateway 应该检查什么；Catalog 告诉 Gateway 应该加载哪个 Provider；Gateway 把执行结果交给审计；治理中心检查这些关系是否完整；Release Gate 再基于权威证据做最终判断。

## 四、一次调用是怎样走完的

### 先说“能力”：它到底替业务完成什么

Capability 不是一堆限制条件，也不是一个被严格保护的函数。它首先是一项能够独立完成的最小业务能力：有人在一个明确场景下调用它，成功后得到一个可以验收的业务结果。治理中的权限、版本、范围、事务和审计，都是为了让这个结果安全、稳定、可证明地发生。

以 `person.height.write@1` 为例，它的目的不是“检查身高有没有超过 2.5m”，也不是“调用一次写数据库函数”。更接近业务的说法是：“为人员档案形成一条单位统一、来源可追溯的身高测量记录，供后续人员配置使用。”这句话就是 `business_effect`；`0 < height <= 2.5m` 是保护这个目的不被错误数据破坏的业务不变量。

可以把关系记成一句话：**能力说明想办成什么事，业务规则说明什么情况下这件事才算办对，技术治理说明谁能用哪一版代码可靠地把它办完。**

![图 3｜业务意图如何变成可证明的业务结果](atomic-capability-explainer-assets/03-invocation-journey.png)

### 图 3 里的业务规则在哪里

图 3 现在有两条并行的检查线。上面的“技术治理线”回答：调用者、版本、权限和代码实现是否可信；下面的“业务治理线”回答：这次请求里的数据和最终业务结果是否合理。两条线必须同时通过，不能用技术合规代替业务正确。

例如 `person.height.write@1` 收到 `height=3.2`、`unit=m`。程序先确认字段确实是数字、单位确实受支持，然后执行业务不变量“统一换算为米后必须满足 `0 < height <= 2.5`”。如果不成立，即使调用者有权限、Capability 版本正确、Provider Hash 也完全一致，仍然必须返回 `HEIGHT_OUT_OF_RANGE`，不能写入数据库。

业务规则也不是全部塞进同一个地方：固定范围和枚举可以写进输入 Schema；需要同时看多个字段、对象当前状态或领域政策的判断，应由 Provider 或正式领域策略执行；数据库可以做最后一道防线，但网页提示和数据库字段类型都不能单独代表完整治理。Catalog 还必须登记规则、执行位置、错误码和测试证据，Release Gate 才能证明“规则不只写在文档里，而是真的执行过”。

### 先不用看代码：把它想成一张正规工厂订单

假设客户想要一个零件。正规工厂不会听完一句话就让车间开工，而是先确认客户要的产品和版本，再检查订单资料与办理条件，然后保证同一张订单不会被重复生产，最后质检并留下交付凭证。Capability 治理做的是同一件事，只不过“产品”换成了业务结果。

![图 3A｜把一次 Capability 调用想成一张正规工厂订单](atomic-capability-explainer-assets/03a-factory-order.png)

这里有两条不同的线：每张订单走“接单到交付”流程；工厂的软件和生产线则走另一条“能否上线”检查。Release Gate 检查的是整套系统版本，不是把每一张用户请求重新发布一次。

### 程序究竟怎样完成一次“核对”

程序不会像人一样“看懂大意”。它收到的是一组有名字的数据字段，然后按已经写好的步骤查记录、取字段、比较值，最后用 `if` 条件决定继续还是拒绝。

![图 3B｜程序完成一次核对时实际做了什么](atomic-capability-explainer-assets/03b-how-code-checks.png)

以版本核对为例，这里通常不是运行 `git diff`，也不是逐字符比较两份代码。请求会带上 `capability_id`、`major_version` 和 `catalog_release`；程序按这些编号去 Catalog 找记录，再比较登记的 Provider 模块、版本和制品 Hash。Hash 可以理解为文件内容计算出的“数字指纹”：内容发生变化，指纹通常也会变化。

### 读懂下面函数前，先认识程序的六种基础动作

- **数据：** 程序收到的不是一句模糊的话，而是 `字段名 = 值` 组成的结构，例如 `major_version = 1`。
- **函数：** 一段被命名的固定操作步骤。调用函数，就是让程序执行这段步骤。
- **查找：** 按 ID 去内存、Catalog 或数据库里找到对应记录；找不到就返回错误。
- **比较：** 检查版本号、状态、Hash 或其他确定值是否相等，或是否符合某个范围。
- **条件判断：** `if` 可以理解为岔路口；条件成立走下一步，不成立走拒绝或异常处理。
- **状态保存：** 把“正在执行、已经完成、失败、结果未知”写入持久化存储，机器重启后仍能查到。

从生活语言过渡到代码时，可以这样理解：`invoke()` 是总接待台；`CatalogResolver` 是查正式服务目录；`authorize()/validate_payload()/approve()` 是审核订单；`ReliabilityCoordinator` 是防重复并保存执行状态；`provider.handler()` 是真正办事的车间；`project()/complete()` 是交付结果和凭证；`evaluate_release_gate()` 是检查整套系统能否上线。

### 给技术人员：这些步骤对应到哪些代码

图里的规则不是靠开发者自觉记住，而是集中写进共享执行链。所有正式消费者最终都把请求包装成 `InvocationEnvelope`，交给 `CapabilityGatewayService.invoke()`；因此同一套检查同时约束网页、插件、Agent、MCP 和其他 Capability。

| 阶段 | 主要代码入口 | 实际完成的事情 |
|---|---|---|
| 身份与版本 | `CapabilityGatewayService._resolve_envelope()`、`CatalogResolver.descriptor()`、`CatalogResolver.resolve()` | 核对 `catalog_release`、`capability_id@major`，找到冻结 Descriptor 和已登记 Provider，并校验 Provider 制品 hash；版本、能力或制品对不上就不执行 |
| 契约与调用资格 | `descriptor.exposure.allows()`、`GatewayPolicy.authorize()`、`validate_payload()`、`GatewayPolicy.approve()` | 检查消费者是否允许、输入 Schema、资源范围、权限、并发版本和 confirmation；**权限只是技术治理中的一项** |
| 业务不变量 | `validate_payload()`、`provider.handler()`、领域策略函数、数据库约束 | Schema 处理静态单字段约束；Provider/领域策略处理跨字段、对象状态和动态政策；失败时返回登记的稳定业务错误码 |
| 可靠执行 | `ReliabilityCoordinator.replay()/begin()`、`AdmissionController.acquire()`、`provider.handler()`、`asyncio.wait_for()` | 在业务规则通过后防止重复写入，取得持久化执行租约，控制容量和截止时间；强一致写入必须返回事务参与者，异常时回滚 |
| 结果与证据 | `validate_payload(..., label="output")`、`GatewayPolicy.project()`、`ReliabilityCoordinator.complete()`、`_record_metric()` | 校验输出契约，按消费者投影数据，持久化结果和证据，再提交事务；如果业务可能已提交但结果没有可靠保存，则返回 `OUTCOME_UNKNOWN`，不能假装成功 |

还有一条与单次调用并行的“能否发布”链：`audit_catalog()` 检查能力登记质量，`evaluate_completion()` 扫描路由、消费者旁路、领域依赖和台账完整性，`evaluate_release_gate()` 汇总静态门禁；受控治理环境再把 `snapshot_gid`、`test_run_gid`、Finding、审批和签名报告组合成正式发布决定。

所以这套治理同时解决三个层次的问题：**每次调用是否正确执行、业务结果是否可靠可证明、承载这些能力的代码版本是否允许发布。**

以网页查询 BOP 版本为例：

1. 网页不是把 API 地址假装成 HTTP 方法，而是提交 `capability_id + major_version + catalog_release + arguments`。
2. Gateway 在指定 Catalog Release 中解析出唯一能力版本 GID、契约和 Provider 制品。
3. Gateway 按契约校验参数、调用者身份、资源范围和消费者资格。
4. 如果是写操作，还要校验确认令牌、幂等键、事务提供者和截止时间。
5. Provider 只在 Craft 领域内完成“查询 BOP 版本”这个业务效果；若需别域数据，只能调用别域正式 Capability。
6. 返回结果必须符合输出契约；错误必须转换为稳定错误码，不能把内部异常原样抛给页面。
7. 审计系统记录调用者、能力版本、请求 GID、目标资源、结果和证据。任一关键检查失败都应当关闭调用，而不是降级绕过。

这也解释了最近调试中出现的两个现象：把 Capability 路径误当成 `fetch` 的 HTTP method，是消费者适配错误；刷新操作缺少 confirmation，是 Gateway 正在执行写操作保护。两者都应该修消费者或契约适配，不能为了“页面先能用”而关掉门禁。

## 五、Capability 自身的版本怎么管理

![图 4｜五种容易混淆的身份与生命周期](atomic-capability-explainer-assets/04-version-lifecycle.png)

版本管理里有五个名字，作用完全不同：

| 名称 | 回答的问题 | 规则 |
|---|---|---|
| `capability_id` | 这是哪一类业务能力？ | 逻辑身份稳定，发布后不得改名复用 |
| `major_version` | 调用契约是否兼容？ | 破坏输入、输出、权限、副作用、事务或错误语义时必须升 major |
| `capability_version_gid` | 这一次具体登记是哪一版？ | 每次正式版本获得不可复用 GID，绑定契约、Provider 与证据 |
| `catalog_release` | 这次部署认可哪一组能力？ | 是整本能力目录的不可变快照，不是单个能力版本号 |
| `snapshot_gid / test_run_gid / release_report` | 谁在什么代码上检查过，结果是什么？ | 属于治理与发布证据，不能由 Catalog 内的静态字段代替 |

生命周期是：`experimental → stable → deprecated → retired`。

- `experimental` 可以试验，但不能冒充正式稳定能力。
- `stable` 表示契约、Provider、消费者和验收条件都已满足正式门槛。
- `deprecated` 仍可在迁移期使用，但必须给出替代能力、截止日期和消费者迁移计划。
- `retired` 只有在登记消费者已迁完、旧路由失效且审计确认无调用后才能进入；历史记录仍需保留。

兼容性修复不一定需要升 major，但也不能原地篡改已冻结的 Catalog。删除字段、改变字段含义、提高权限要求、改变副作用或事务边界，都是破坏性变更，必须发布新 major。

## 六、系统如何保证大家真的照制度执行

制度写在文档里远远不够。AI00 采用四道防线：

![图 5｜设计、构建、运行、发布四道防线](atomic-capability-explainer-assets/05-four-gates.png)

### 第一道：设计时

新增或修改能力必须明确 owner、唯一业务效果、Schema、错误、权限、事务、幂等、副作用、Provider、API 和消费者。原子性不成立或跨域归属不清时，不应进入 stable。

### 第二道：构建时

脚本自动生成并校验 Catalog、能力文档、验收清单、用户功能映射和领域依赖；扫描 Web、API、插件、Agent、Provider、迁移与表所有权，发现未绑定入口、跨域 import、跨域 SQL、过期 hash 或未登记消费者。

### 第三道：运行时

所有正式调用通过 Gateway。权限、资源选择、消费者资格、确认令牌、幂等、超时、输入输出 Schema 和 Provider 装载都在服务端执行，不能只靠前端隐藏按钮。

### 第四道：发布时

Release Gate 必须从权威存储重新读取当前提交对应的 Registry 快照、测试运行、Finding、审批和签名结果。调用者自报的 `findings=[]` 或 Catalog 里的静态 `pass` 不算发布证据。

任何一道都可能发现前一道遗漏的问题，因此“某一轮门禁 OK”不等于以后不会出现新问题。真正可靠的是：检查规则版本固定、输入范围完整、证据绑定当前提交、结果可复现，而且阻断项真的能阻断发布。

## 七、479 个能力是否需要 479 份不同测试文件

不需要。

当前有 479 个 stable Capability。每个 stable 能力必须声明 7 类强制验收场景，所以有 `479 × 7 = 3353` 条能力级验收声明。这是**能力与测试场景的对应关系**，不是要求写 3353 个文件，也不是要求每个能力单独复制一套测试代码。

同一套参数化测试可以覆盖很多能力，但每条证据必须能反查到：测试了哪个 `capability_version_gid`、基于哪个 `snapshot_gid`、运行在哪个 `code_revision`、由哪个 `test_run_gid` 产生，以及结果哈希是什么。

当前离线严格验收汇总为 3364 passed，说明静态契约和离线验证已具备较高覆盖度；但 Agent、后端 Gateway、本地运行时、MCP、插件等真实组件的受控环境探针仍必须生成自己的运行证据。**离线通过不等于生产候选已经取得签名放行报告。**

## 八、这套机制仍可能有哪些漏洞

治理不是一次性“清零 Finding”，而是持续确保事实和登记一致。当前最值得共同检查的是：

| 风险 | 可能发生什么 | 应怎样发现 |
|---|---|---|
| 扫描范围有盲区 | 动态拼接路由、未纳入目录的前端或新插件绕过扫描 | 维护完整入口台账，扫描结果与实际制品清单对账 |
| 登记有字段、没有事实 | `consumer_refs`、测试结果或 Provider hash 只是占位 | 抽样回到代码、运行日志和制品验证，不接受自报状态 |
| 权限过宽 | 有权限策略，但资源选择器实际允许越权访问 | 做角色 × 租户 × 项目 × 资源矩阵测试 |
| 外部副作用失控 | 数据库回滚了，但消息、文件或第三方调用已经发生 | 写能力必须声明参与者、补偿策略和结果未知处理 |
| 兼容门面长期存在 | 已登记 `split` 的通用操作仍被新消费者继续调用 | 门禁禁止新增引用，并给旧消费者设迁移截止日期 |
| 旧证据误当新证据 | 测试通过，但测试的是旧提交、旧 Provider 或旧 Catalog | 强制比对 commit、artifact hash、snapshot 与 release report |
| 工作树不干净 | 审计对象与最终提交内容不一致 | 只对明确提交重新生成最终快照和签名报告 |
| 治理中心自己绕过治理 | 扫描、分析、发布接口直接改 Store 或接受调用方自报 | 治理能力自身也必须经 Gateway、权限、确认、幂等与审计 |

## 九、以后一起评审时，只问这 12 个问题

面对任何新增页面、API、插件或 Agent 动作，我们可以依次问：

1. 它最终要产生的唯一业务结果是什么？
2. 现有 Capability 能否承载，为什么需要新增？
3. 哪个领域和哪个 owner 对结果负责？
4. 输入、输出和稳定错误分别是什么？
5. 谁能调用，权限要限制到哪个资源范围？
6. 是否写数据；确认、幂等、事务和补偿怎么做？
7. Provider 在哪个模块，制品 hash 是否与登记一致？
8. 哪些 Web、API、插件、Agent 或任务是真实消费者？
9. 是否存在绕过 Gateway 的 REST、内部 import、SQL 或数据库直连？
10. 测试是否覆盖成功、拒绝、边界、重复请求和依赖失败？
11. 证据是否绑定当前 GID、快照、提交和测试运行？
12. 当前 Release Gate 能否用权威证据重算并阻断发布？

如果这 12 个问题都能用事实回答，治理就不是“填表”；如果只能回答“应该是”“代码里大概有”，那就是需要继续查的漏洞。

## 十、最后记住一张心智地图

- 规范是法律：规定什么叫合规。
- Descriptor 是办事指南：说明能力承诺什么。
- Registry 与 Catalog 是户籍和目录：证明能力身份与当前可用版本。
- Gateway 是检查站：保证每次调用都按契约进出。
- Provider 是办事窗口：在领域边界内完成真实业务效果。
- Evidence 与 Audit 是黑匣子：证明发生过什么。
- Governance Center 是治理部门：持续发现关系断裂、冲突和缺证据。
- Release Gate 是出厂总闸门：证据不完整，就不能发布。

这套系统的目标不是让开发变慢，而是让 AI00 在能力越来越多、消费者越来越多、多人和 Agent 并行开发时，仍然做到：**能找到、能理解、能授权、能替换、能审计、能证明、也能真正拦住不合规版本。**
